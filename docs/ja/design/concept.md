# inka — コンセプト

inka が何であるか、そしてすべてがそこから従う中核の考え方。
英語版(正): [English](https://www.space.t.u-tokyo.ac.jp/inka/design/concept/)

## 問題

イタレーティブに開発されるシステムの保証論証は腐る。承認は文書に付随する儀式になり、
何かが変わったとき「全部無効」か「何も無効にしない」かの二択になり、記録は機械検証
できない。inka は論証・承認・失効を*コード*にする: リポジトリ内のテキストであり、
純関数で評価される。

## 中核の考え方

1. **世界には命題しかない。** ノードは自然言語の契約(description)を持つ命題であり、
   ブロックキーワードとして宣言される3つのモードのいずれかで**履行**される:
   `structure`(子への分解)、`bind`(機械検証可能な証拠への束縛)、`fiat`(論証なしの
   受諾。葉のみ)。ルートは唯一の `objective` で、その文言自体も承認対象の
   契約である — ルートへの合意も他のすべてと同様に inka の中に記録される。
   モードは承認対象と1対1に対応する。

2. **承認は局所ビューに束縛される。** ノードの局所ビュー = 自身の展開済み
   description + 期限注釈 + 直接の子の description 群。それより深くは含まない。
   すべての承認レコードはこのビューのハッシュを持つ。帰結: description の編集で
   失効するのは当該ノード自身の承認と直接親の structure 承認だけ。rename と子の
   並べ替えは何も失効させない(ID・タグ・コメントは契約に含まれない)。再承認の
   コストは差分に比例する。

3. **真実性と妥当性の分離。** 証拠が*通る*かは機械の真実であり、証拠の再実行で
   再確立される。eval は記録された結果を照合するだけ。その証拠がこの命題に
   *適切*かは人間の妥当性判断 — bind 承認である。証拠が依拠する仮定は界面を貫通して
   集約され、証拠の境界で提示される。

4. **承認の意味論。** ラベルは approve / decline / cannot-take-responsibility。
   現在ハッシュへの decline は拒否権であり、クォーラムでは覆らない。`established` は
   DAG 上の不動点(fiat 承認 ∨ structure 承認 ∧ 全子 established ∨ bind 承認 ∧
   証拠 pass。objective は自身の承認+全子 established を要する)。
   eval はリポジトリの内容だけを読む — 時計もネットワークも使わないので、
   同一コミットは常に同一に評価される。

5. **ポリシーはレビュー可能なテキスト。** どの対象に誰の承認が要るかを、セレクタ
   (モード × id/名前空間/`#tag`)と述語(`any`, `role`, `including`, `not-author`,
   `fresh`, `forbidden`, …)で書く。フェーズは全順序を宣言し、`fresh` は記録された
   フェーズを比較する(タイムスタンプは使わない)。期限注釈で書き手が期限付きの
   負債を宣言できる: どのノードにも `until: <phase>` と引用符付きの `reason:` を
   書ける(`reason:` と `promote:` は `until:` がある場合のみ)。`promote:` は
   後継モードの宣言で、fiat では `structure` | `bind`、objective では
   `structure` のみ。**失効はハード** — 期限を過ぎたらそのノードの承認は新規のものも含めて一切
   カウントされないので、「このまま維持する」には注釈を目に見える形で編集する
   (=契約変更)しかなく、黙った再承認では覆せない。

6. **値も契約である。** description 内の `{$var}` は TOML から解決され、契約は
   **展開後**にハッシュされる。要求値を1つ変えると、それを参照する全契約が正確に
   失効する。

7. **記録は監査可能。** 承認は追記専用の jsonl で、1行が自己完結したレコードであり、
   承認時点のフェーズを刻む。署名とアンカリングは後から完全性を強化する。スキーマは
   初日からそのフィールドの席を確保している。

## ライフサイクル

命題は典型的には `fiat` + `until:` / `promote:` / `reason:`(明示的で期限付きの負債)
から始まり、証拠ができたら `bind` に、分解されたら `structure` になる。根拠が弱いと
感じる structure / bind には `until:` + `reason:` を書き、「期限までに children / source
を見直す」義務として残す。親は子の description にしか束縛されないため、子のモード
遷移も注釈も親の承認を失効させない。
