# テスト証拠: 連携契約と実装状況

2026-09-11 に利用者と確認した [#21](https://github.com/ut-issl/inka/issues/21) の方針。
英語版（正）: [English](../../en/design/test-evidence-integration.md)。
本書は導入体験の要件、[意味論](ci-evidence.md)は承認・評価の契約を定義する。
実装例は下記の追従状況と併せて読む。試作が動作することと、この要件を満たすことは別である。

## 目的と名称

既存のソフトウェアテストを、veriq のグラフとして作り直さずに論証へ接続する。
veriq は解析の構造化された界面・接続を、テスト証拠は確認可能なテストと実結果を扱う。
CI は実行の場、GitHub Actions は収集・配送手段であり、証拠の種類ではない。

公開概念を「テスト証拠 / test evidence」、DSL を `test:` とする。
`ci:` は移行後に廃止し、恒久的な別名にはしない。構文実装・fixture 移行・廃止時期は
関連Issue: #66/#73 が扱う。現在の実装ブランチはまだ `ci:` を受理するため、`test:` の例を
実装済みとして示さない。改名だけを理由に凍結済みhash・record・bundleの版は変えない。
内部の版付き識別子に残る `ci` はプロトコル識別子であり、承認失効の理由にしない。

## 必須の利用体験

テスト作成者は通常のテストを書く。対応する連携では、inka専用デコレータ、個別登録、
手書きの選択JSON、プロジェクトのテスト設定ファイルへのinka専用変更を要求しない。

CI管理者が一度workflowを設定する。準備・収集Actionの追加と、workflow内の最小限の
レポート出力オプション・環境変数設定は許容する。既存テストは独立したstepとして実行し、
従来どおりCIのOK/NGを決める。inkaのAction内でしか実行できる構成にはしない。
言語環境の構築は証拠元が引き続き所有し、通常の連携でテストの二重実行を要求しない。

既存コマンドが収集する全テストを原則自動で証拠化する。その範囲に追加したテストは
inka向けの登録不要。bind先は論証側が選び、証拠元の公開範囲の絞り込みは任意設定とする。
公開フィルターは既存CIが実行するテストを変更しない。公開しても承認や論証への追加は自動化しない。

## 収集経路

十分なケース識別・必要集合・結果・実行したソースとの対応を持つ既存レポートがあれば再利用する。
不足する場合は、workflow内でレポート出力またはフレームワーク連携を有効にする。
inkaの準備Actionで実行前のソースを記録し、通常のテストstepの後に収集Actionを置いてよい。
ランナーごとの内部連携はinka側が保守し、証拠元のrunnerで動かす。受信側にテスト環境は不要。

収集は既存job内の後続stepでも、レポート・ソースsnapshot/receiptを明示的に渡す別jobでもよい。
別jobは元jobのworkspaceを直接読めると仮定しない。job全体のOK/NGだけでは個別テストの証拠にしない。
ログや汎用レポートは、実際に契約に必要な情報を持つ場合にだけ利用できる。

コマンドを実行するwrapperは任意の便宜機能として提供できるが、唯一の連携にしない。
再利用できない場合の別実行は明示的に選択し、元のCIとは独立した実行の証拠として記録する。
暗黙の再実行はしない。

## 必要集合・ソース・失敗

- 必要ケースは成功結果だけから推測しない。途中中断で必要集合を縮めない。
- 必要ケース・環境の全件passでのみ成立し得る。skip・cancel・欠落は不成立。
  実行・試行・環境を識別し、再試行の成功結果を自動混合しない。
- 実行前snapshotまたは同等の対応付けで、結果と実際のソースを結ぶ。
  実行後にcheckoutしただけでは十分ではない。情報不足・不整合はエラーとする。
- 既存テストstepの失敗を維持したまま失敗結果を収集する。収集エラーも明示する。
  runner消失や強制中断ではArtifactが生成できない場合があり、欠落を成功扱いしない。
- 自動公開の範囲はコマンドの収集対象であり、リポジトリ中のあらゆるテストではない。
  既存対象の必要集合の変更は再承認を要求し、無関係な対象の追加はそのhashを変えない。
- 公開すると約束した範囲の対応外・曖昧なテストを黙って除外したり成功扱いしたりしない。
  エラーと制限を示し、必要なら明示的な公開フィルターで範囲を絞る。

## 維持する合意

ファイル・関数単位の証拠を扱う。初期対象はRust/libtest/proptest、Python/pytest、
JavaScript/TypeScript/Vitest、ActionはLinux。関連属性・デコレータ・テスト宣言を抽出し、
外部helper・fixture本文は関数契約に含めない。全実行依存の捕捉は#39の別課題。

証拠元ID・対象ID・粒度・抽出規則・CRLFのみ正規化した本文・必要集合がinterface hashを決める。
識別や必要集合の変更は再承認、結果だけの変更では承認を失効させない。
有効な承認とpass証拠の両方でbindが成立する。不正な証拠はCLI入力エラー、
解釈可能な欠落・非passはbindのblameとする。

取り込んだ版だけをオフライン評価する。upstreamのcheckout・runner・ネットワークは不要。
未取り込みの更新は影響しない。環境・lockfile情報は任意。署名#38、承認CLI#27、
自動追従、依存closureのポリシーは別課題として維持する。

## 実装前に残る確認事項

上記の要件は確定済み。Actionの正確な名前・入力・配布方式、ランナーごとのreport/hook、
自動生成する対象・ケースIDの安定性、containerや複数binary等の対応範囲、ci:の廃止時期は
具体案を利用者に確認してから実装する。試作の挙動を暗黙の決定にしない。
関連Issue: #66・#68〜#71に担当する未決事項を残す。
