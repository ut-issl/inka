# calc 証拠の契約

英語版（正）: [English](../../en/design/calc-evidence.md)。

## 責務分担

calc 証拠とは、計算グラフ — ルートモデル・計算・検証のノードが互いに依存するグラフ。
[veriq](https://github.com/ut-issl/veriq) がデコレータ付き Python 関数から構築するもの — から得る証拠である。
bind はそのグラフの検証1つを `calc: "<path>"` で参照する。最初の producer は veriq であり、契約は veriq の
グラフに合わせて形作られている: 定義の `kind` は veriq の3種類のノード種別のいずれかである。ただし veriq
そのものを要求する箇所はないので、グラフをこの種別に対応づけられる別の producer も同じ証拠を出力できる。

inka の project があるレポジトリをプロジェクトレポジトリ、計算グラフが含まれるレポジトリをソースレポジトリと
定義する。両者は同一のレポジトリでもよい。

ソースレポジトリが自身の環境でグラフを評価する。アダプター — veriq では Python パッケージ `inka-evidence` の
`inka-evidence-veriq` — を使って、inka の project が calc 証拠として認識できる証拠 json ファイルを出力する。
保存と配送は[テスト証拠](test-evidence.md)とまったく同様に capsula が担う: ソースレポジトリは capsula の run
として評価し、json を run の成果物として保存し、プロジェクトレポジトリは設定されたパスからそれを読む。inka は
保存・配送機構を実装せず、評価は取り込んだ版に対してオフラインで行う。Python インタプリタも veriq もネットワークも
必要としない。

Rust は Python を決してパースしない。グラフのソースを読む唯一の構成要素はアダプターであり、inka に必要な
ものはすべて json の中にある。

証拠のターゲットが inka の命題と対応しているかの判断は、bind ノードに対する review(人間の承認)が担う。
レビュアーが見るものは以下で定義する: 関数1つではなく、それが依って立つすべてである。

## inka の bind 用証拠 json ファイル

bind は `calc: "<path>"` で証拠を参照する。path は producer のグラフにおけるターゲット検証のパスであり、
veriq では `Scope::?検証名`、例えば `calc: "Power::?verify_margin"` である。inka はこれを読み込んだ証拠の
パスとバイト単位で比較するだけで、それ以外は何も解釈しない。読み込んだ証拠の中でターゲットパスが重複した場合は
入力エラーとする。

証拠 json はリポジトリ直下の `schemas/calc-evidence-v1.schema.json` に従う。ターゲットごとに次を記載する。

- **path** — bind が参照するターゲットパス。
- **definitions** — ターゲットの**定義粒度の上流部分グラフ**(ターゲット自身を含む): ターゲットが依存する
  すべてのルートモデル・計算・検証を、それぞれちょうど1回ずつ、`path`・`kind`(`model` / `calculation` /
  `verification`)・人間が確認できる `source` 文字列とともに並べたもの。定義のテキストをどこまで含めるか
  (デコレータ、シグネチャ、docstring)はアダプターの抽出責務であり、inka は言語固有の構文を解析・実行しない。
  定義粒度とは、出力のリーフごとではなく定義ごとに1項目という意味である: テーブルを返す計算は、ターゲットが
  そのセルをいくつ使おうと1つの定義である。
- **assumes** — 上流部分グラフが仮定する inka ノードを、完全修飾の inka ノード ID(`namespace::id`。
  直下のノードは素の `id`)で並べたもの。アダプターは producer のノードメタデータからこれを集め、定義にわたって
  和集合を取るので、各 ID は1回だけ現れる。[仮定](#仮定)を参照。
- **leaves** — ターゲットの必要リーフ結果: 検証の出力のリーフごとに1項目、`id` で識別し、真偽値の `result` を
  持つ。スカラーの検証はリーフを1つ持ち、ターゲットパスで識別する。テーブル値の検証はセルごとに1つのリーフを
  持つ。リスト全体が必要集合であり、`result` を省略した項目は「宣言されたが結果が欠落したリーフ」を意味する。
  項目は1件以上とし、リーフ ID の重複は入力エラー。
- **valid** — producer 自身の妥当性条件がターゲットについて成り立つか。veriq では `@vq.assume` の機構がこれに
  あたる: 上流が別の検証を前提にしている検証は、その検証が失敗すると invalid になる。前提にされた検証は
  ターゲットの上流部分グラフの一部なので、その定義と、それが仮定する論証ノードは、他の依存先と同じく
  ターゲットの `definitions` と `assumes` に入る。
- **xfail** — producer がターゲットを「失敗が期待される」と印づけているか。省略可。既定は false。

ファイル先頭の **provenance** には、評価したソースの版や capsula の run ID などの記録情報を書く。承認対象には
含めず、inka は未知のキーを無視する。

```json
{
  "v": 1,
  "provenance": {
    "source_revision": "4f2a1c9",
    "capsula_run_id": "01K8WSYC91YAE21R7CWHQ4KYN2"
  },
  "targets": [
    {
      "path": "Power::?verify_margin",
      "definitions": [
        { "path": "Power::$Config", "kind": "model", "source": "class Config(BaseModel): ..." },
        { "path": "Power::@budget", "kind": "calculation", "source": "def budget(...): ..." },
        { "path": "Power::?verify_margin", "kind": "verification", "source": "def verify_margin(...): ..." }
      ],
      "assumes": ["power::eclipse_model_valid"],
      "leaves": [{ "id": "Power::?verify_margin", "result": true }],
      "valid": true
    }
  ]
}
```

ソースはダイジェストだけでなく確認可能な形で含める。inka はこれを承認インターフェースに提示する。証拠 json は
宣言されたダイジェストを運ばない: inka が読み込み時にインターフェースハッシュを計算し、輸送中の内容の検証は
capsula の責務である。

必要リーフ集合は証拠 json 自身が宣言する。成功した結果だけから推定したり、中断した評価で縮めたり、別々の run の
成功を寄せ集めたりしてはならない。

inka はファイルを厳格に読む。契約に反するファイルは入力エラーであり、弱い証拠として扱うことはない。

- 1 以外のバージョン、または `provenance` の外にある未知のキー。
- 空である、または空白を含むターゲットパス・定義パス・リーフ ID。空白とは Unicode の `White_Space`
  プロパティを持つ文字であり、`calc:` の値に課す規則と同じである。
- 定義が1つもない、定義パスが重複している、ソースが空である、または自身のパスの定義を持たないターゲット。
- 完全修飾のノード ID でない仮定、または重複した仮定。
- リーフが1つもない、またはリーフ ID が重複しているターゲット。
- 省略ではなく `null` と書かれた `result` や `provenance`。
- 読み込んだ証拠の中に2回以上現れるターゲットパス。

### veriq アダプターがソースに含めるもの

`source` に何が入るかが、承認の及ぶ範囲を決める。出力されたソースの外側を変更しても、インターフェースハッシュは
変わらず、承認もそのまま残る。`inka-evidence-veriq` は定義ごとに次を出力する。

- 定義自身のテキスト — ルートモデルのクラス、または計算・検証の関数(デコレーターを含む)。
- そのテキストから、ルートモデルのフィールドまたは関数の戻り値注釈を起点に、型引数・PEP 695 の型エイリアス・
  基底クラスを辿って到達するプロジェクトのクラスすべて。各クラスは1回だけ、名前順に並べる。`@vq.with_range` が
  生成した enum は自身のテキストを持たないので、メンバーの一覧として出力する。

次は含めない。

- veriq・pydantic・Python 標準ライブラリのクラス。これらを更新しても承認は無効にならない。それ以外のパッケージの
  クラスはプロジェクトのコードとして扱う。標準ライブラリのモジュールと同じ名前を持つプロジェクトのモジュール
  (`profile.py` や `test` パッケージ)のクラスも同様である。判定に使うのはモジュールの名前ではなく、読み込み元の
  場所である。
- 関数が呼び出すだけ、読むだけのもの: ヘルパー関数、モジュールレベルの定数、import した値。ヘルパーを編集すると、
  ハッシュ対象のソースがどれも変わらないまま検証の結果が変わりうる。変更のたびに再承認が必要なロジックは veriq の
  計算として書く。そうすれば、それ自体が1つの定義になる。

アダプターは、見かけより弱い証拠を出力するくらいなら、何も書かずにエラーで停止する。次のものを拒否する。

- 真偽値でも欠落でもないリーフ結果。
- `assumes` の下の文字列リスト以外の `inka` メタデータ。
- 検証を1つも定義しないプロジェクト。
- 解決できない名前を含む戻り値注釈または型エイリアス。その先のクラスを辿れないためである。
- 同じ修飾名で到達する、内容の異なる2つのクラス。ソースには各名前が1回しか載らないので、もう一方のクラスが
  ハッシュから漏れるためである。

## 仮定

仮定とは、証拠が確立することなく依拠している命題である: 現実を包絡しているとみなすモデル、完全であるとみなす
テーブル。inka にはそのような命題の置き場所がすでにある — 論証のノード、通常は `fiat` ノードであり、承認または
自身の子によって discharge される。したがって論証そのものが仮定のレジストリであり、論証と歩調を合わせるべき
第2の仮定文リストは存在しない。

calc の producer は、ある定義がどの論証ノードを仮定するかを、その定義のユーザーメタデータの `inka` キーの下で
宣言する:

```python
@power.calculation(metadata={"inka": {"assumes": ["power::eclipse_model_valid"]}})
def budget(config: Config) -> PowerBudget: ...
```

各項目は完全修飾の inka ノード ID である。producer は文字列を保持するだけで他には何もしない。ID が実在するかは
inka の仕事である。

仮定はグラフの構造を通じて自動的に集約される。手作業ではない: アダプターはターゲットの定義粒度の上流部分グラフを
取り、その中のすべての定義の宣言済み ID を集めて和集合を取る。どのモードのノードも仮定できる。その結果が
ターゲットの `assumes` リストであり、inka はこれを3つのことに使う。

- **ハッシュ。** 仮定ノードの展開済み description を、通常の description と同じく正規化してバイト列順に
  ソートしたものが、bind のビューハッシュの仮定スロットを埋める([内容のハッシュ](#内容のハッシュと再承認)を
  参照)。仮定の文言を変えると bind の承認は無効になる。スロットに ID は入らないので、ノードの改名だけでは
  無効にならない。ただし veriq のデコレータのように、ハッシュ対象のソースの中に ID を書く producer では、
  改名でそのソースが変わり、インターフェースハッシュも変わる。
- **依存。** calc の bind は、自身の承認と pass した証拠に加えて、仮定するすべてのノードが established である
  ときに限り established になる。まだ discharge されていない仮定 — 未承認の fiat、失効した期限 — は、その
  ノードを原因として bind を unestablished のままにする。
- **提示。** 仮定集合は各ノードの ID と description とともに、bind 承認時にソースの隣に表示され、前回承認からの
  変化が diff として表示される([承認スナップショット](#承認スナップショットと-diff)を参照)。

### 読み込み時の構造

仮定は論証グラフの辺であるため、inka は calc 証拠の構造部分 — ターゲット、定義、仮定 ID — を、評価時だけ
でなくプロジェクトの読み込み時に読む。読み込んだ証拠がターゲットを提供している `calc:` bind ごとに、その
ターゲットが仮定する各ノードへ bind から仮定の辺を張る。仮定 ID はノードの完全修飾 ID(`namespace::id`、
ルート直下のノードなら素の `id`)と完全一致で照合する。証拠はどの名前空間にも属さないので、`children:` 参照
と違って接頭辞を省略することはできない。
どちらの辺も依存である: 評価の順序を決め、循環を閉じ、仮定の辺だけが到達するノードも objective から到達
しているとみなされ、孤立ノードではない。異なるのは、仮定されたノードは子ではないこと。`children:` は宣言
された構造のままで、bind が依存するのは仮定されたノード自身の成立である。

`inka check` は次を、bind の `calc:` プロパティを位置としてエラー報告する。

- 論証のどのノードも指さない仮定 ID。
- 仮定の辺を通る依存の循環。例えば、証拠が bind 自身やその祖先を仮定している bind。循環上のノードを順に
  列挙し、仮定の辺は `⇢` で描く:
  `dependency cycle through an assumption: branch → modelled ⇢ root → branch`。
  循環は、互いに依存し合うノードの組ごとに 1 つ報告する。その組が `children:` 参照だけの循環も含む場合は、
  通常の `children:` の循環と同じ形でそちらを報告する(`dependency cycle: x → y → x`、位置は先頭ノード)。
  それは書かれた論証そのものにある循環で、証拠が何を言っても残るからである。

リーフの結果、妥当性、`xfail` は評価だけが読む。読み込んだ証拠にターゲットが存在しない `calc:` 参照は check の
エラーではない。それは証拠の欠落であり、`inka eval` が unestablished な bind として報告する。`calc:` の値自体は
check 時に形式検査を受ける: 空でなく、1行で、空白を含まないこと。設定された calc 証拠ファイルが存在しない、
または不正な場合は、テスト証拠と同様、すべてのコマンドにとっての入力エラーである。

## 内容のハッシュと再承認

インターフェースハッシュは、ターゲットパス、上流部分グラフの各定義のパスとソース、必要リーフ ID 集合を覆う。
ソースの正規化は CRLF を LF に置き換えるだけで、コメント・整形・Unicode 正規化状態・インデント・行末空白は
内容のままとする。フレーミングは[確定仕様](spec.md)のビューハッシュと同じ規則(u64-LE の長さ接頭辞付き
`field` / `list` / `entries`)を使う。

```text
preimage = field("inka:calc-evidence:v1") ‖ field(target path)
           ‖ entries(definitions) ‖ list(required leaf IDs)
entries(definitions) = u64-LE(count) ‖ field(path[0]) ‖ field(normalized source[0]) ‖ ...
interface_hash = SHA-256(preimage)
```

定義はパスのバイト列順で、リーフ ID もバイト列順でソートする: producer が並べた順序は編集ではない。定義の `kind` は
表示用のメタデータでハッシュに入らない。結果、妥当性、`xfail`、provenance もハッシュに入らない。

bind のビューハッシュは凍結済みの v1 レイアウトを保ち、calc の bind では仮定スロットが埋まる。

```text
bind = field("inka:bind:v1") ‖ field(desc) ‖ list(annotations) ‖ list(comments)
       ‖ field(interface_hash) ‖ list(assumptions)
assumptions = 仮定ノードの正規化済み description をバイト列順にソートしたもの
```

test の bind のスロットは空のままなので、calc 証拠以前に凍結されたベクタは変わらない。レイアウトは
`tests/golden/hash/calc-evidence-v1/` と `tests/golden/hash/v1/` のベクタで凍結する。

したがって、次の場合に再承認が必要になる。

- 上流のいずれかの定義のソースが変わった — 承認者は検証を、それが依って立つ計算とモデル*とともに*判断した。
- 上流の定義が追加・削除・改名された。
- 必要リーフ集合が変わった。
- 仮定ノードの description が変わった、または仮定集合にノードが増減した。

同じインターフェースと同じ仮定集合に対する新しい結果は、既存の承認で評価できる。stale な承認と証拠の失敗は
テスト証拠と同様に独立した原因として報告する。

## bind の評価

ノードが失効しておらず有効な decline もないとき、calc の bind は、有効な承認があり、証拠が pass し、仮定する
すべてのノードが established であれば established になる。既存の承認クォーラム・拒否権・失効の規則は引き続き
適用される。

証拠が pass するのは、すべての必要リーフが `result: true` で、`valid` が true で、`xfail` が false のときである。

| 観測された状態 | bind にとっての意味 |
| --- | --- |
| すべての必要リーフが `true`、`valid`、`xfail` でない | 証拠は bind を確立しうる |
| いずれかの必要リーフが `false` | 証拠は bind を確立しない |
| 必要リーフに結果がない | 証拠は bind を確立しない |
| `valid` が false | 証拠は bind を確立しない |
| `xfail` が true | 証拠は bind を確立しない(期待された失敗) |
| 参照されたターゲットパスが証拠に存在しない | 証拠の欠落。未確立 |
| 仮定ノードが established でない | 未確立。仮定が原因 |
| 契約に反するファイル(例: ターゲットパスの重複) | 読み込み時の入力エラー。何も評価しない |

| 取り込んだ証拠・論証・承認 | 評価 |
| --- | --- |
| ソース A、一致する承認、全リーフ pass、仮定は established | established |
| 一致する承認、リーフが1つ fail | 未確立。証拠の失敗 |
| pass する証拠、承認なし | 未確立。承認の欠落 |
| 上流の計算を編集、承認は旧ソースに対するもの | 未確立。stale な承認 |
| 同じソース、新しい pass する評価 | 承認は有効のまま。established |
| 同じソース、仮定する fiat が未承認 | 未確立。仮定が established でない |
| 同じソース、仮定ノードの description を編集 | 変更後の契約が承認されるまで未確立 |
| 仮定ノードを改名、ID はハッシュ対象のソースの外にある | 改名前と同じ結果 |
| 仮定ノードを改名、ID がハッシュ対象のソースに書かれている(veriq) | 未確立。stale な承認 |
| 同じソース、上流に `assumes` 項目を追加 | 変更後の契約が承認されるまで未確立 |
| 同じソース、別のターゲットパス | 変更後のインターフェースが承認されるまで未確立 |

## 承認スナップショットと diff

bind の承認はハッシュに結びつく。再承認を求められたレビュアーは何が変わったかを知りたい。calc の bind で
興味深い変化はしばしば仮定集合なので、`inka review` は承認した内容を記録し、次回にその差分を表示する。

calc の bind を承認すると、`inka review` は `approvals/snapshots/<view_hash>.json` を書く。`<view_hash>` は
承認したハッシュの hex ダイジェストである。ファイルには、ターゲットパス、仮定集合(各ノードの ID と展開済み
description)、定義(パス・種別・ソース)を記録する。ファイルは内容アドレスであり、正規形で保存する。定義は
パスのバイト順に並べ、ソースの CRLF は LF として扱う。これはインターフェースハッシュの読み方と同じである。
したがって、同じビューを承認する2人の承認者は、証拠がどう配送されていても同じファイルを書き、追記は起きない。
ノードの ID と定義の `kind` はハッシュの対象外である。これらについては最初の承認が書いたファイルがそのまま残り、
同じビューを後から承認しても書き直さない。

スナップショットはレコードより先に書く。書き込みは一時ファイルを作って改名する方式なので、ファイルは完全な形で
現れるか、まったく現れないかのどちらかである。書き込めなかった場合、承認は記録されず、コマンドはその旨を
報告する。コマンドを再実行すれば足りる。decline ではスナップショットを書かない。

```json
{
  "v": 1,
  "target": "Power::?verify_margin",
  "assumptions": [
    { "id": "eclipse_model_valid", "description": "The eclipse model envelopes …" }
  ],
  "definitions": [
    { "path": "Power::?verify_margin", "kind": "verification", "source": "@power.verification()\n…" }
  ]
}
```

review 時には、現在の仮定集合を、同じターゲットの直近に承認されたビューハッシュのスナップショット — その
bind に対する最新の `approve` レコードのうちスナップショットが存在するもの — と比較し、追加・削除・文言
変更された仮定として表示する。「最新」はレコードのタイムスタンプで決める。`inka review` がタイムスタンプを読むのは
この用途だけであり、同じ時刻のレコードは読み込んだ順を保つ。スナップショットが存在しない場合はその旨を伝え、
集合全体を表示する。ソースは全文を表示する。ソースの diff はこの設計の範囲外である。bind は次のように提示される。

```text
  calc: "Power::?verify_margin"
  sources:
    Power::?verify_margin (verification)
      @power.verification()
      def verify_margin(b: Budget) -> bool: …
  leaves:
    Power::?verify_margin: true
  valid: true
  assumes: (2 nodes; changed since the approval by iwata at 2026-09-10T08:30:00Z)
    + battery_model_valid
        The battery model is conservative
    = eclipse_model_valid
        The eclipse model envelopes …
    ~ loads_complete
        The load table covers every mode, safe mode included
        (was) The load table covers every mode
```

`=` は変更なし、`+` は追加、`-` は削除(以前の文言を `(was)` として併記)、`~` は文言変更。仮定は ID で
突き合わせるので、ノードの改名はハッシュが変わらなくても削除+追加として表示される。空の集合は
`assumes: (none)` と表示する。基準の承認以降に bind の参照先が変わっている場合(スナップショットが別の
ターゲットパスを記録している場合)は、先頭に `~ target: <現在のパス>` を表示し、以前のパスを `(was)` として
併記する。その下の diff は、参照先の変更をまたいだ比較になる。

スナップショットは提示の補助である。`inka eval` は決して読まないので、スナップショットの欠落・削除・破損は
レビュアーに見えるものを変えるだけで、何が established かは変えない。すべてのレビュアーが同じ基準を見るように、
承認と一緒にコミットする。

基準のスナップショットが存在するのに読めない場合(途中で切れている、形式が壊れている、このビルドが知らない
フォーマットバージョンである)でも、review は止まらない。`inka review` はファイル名を示す `warning:` を1行
出力し、初回の承認と同じく bind の全体を提示する。どの判断も引き続き選べる。読める古いスナップショットで
代用することはない。それは直近に承認された内容ではないからである。壊れたファイルは、同じビューを次に承認した
ときに置き換える。別バージョンのファイルには手を付けない。

大きな仮定集合は当面素朴に提示する。グルーピングや diff のみの表示は[未決事項](open-questions.md)。

## capsula による配送

配送は[テスト証拠](test-evidence.md#capsula経由の配送)の手順に従い、テストのアダプターの代わりに veriq の
アダプターを使う。

```console
$ capsula run -- inka-evidence-veriq path/to/project.py --input project.in.toml \
    --output calc-evidence.json --provenance source_revision=$(git rev-parse HEAD)
$ capsula push <RUN_NAME>
```

プロジェクト側では、テスト証拠と同様に run を pull し、成果物を設定されたパスへコピーし、`capsula_run_id` を
確認する。project は calc 証拠ファイルをテスト証拠ファイルとは別のキーで指定する。

```toml
[evidence]
tests = ["evidence/test-evidence.json"]
calcs = ["evidence/calc-evidence.json"]
```

以後 `inka check` と `inka eval` は通常どおり設定されたパスを読む。ターゲットのパスは `calcs` に並べた
すべてのファイルを通して一意でなければならない。2 つ目のファイルが同じターゲットを届けた場合や、同じ
ファイルを 2 回並べた場合は、両方のファイル名を示す入力エラーになる。

`tests` は、テスト証拠が唯一の種類だった頃は `files` という名前だった。`[evidence] files` のままの
manifest は、改名を伝えるメッセージとともに拒否される。フォールバックはない。
