# CI証拠の契約

[#21](https://github.com/ut-issl/inka/issues/21)配下の
[#65](https://github.com/ut-issl/inka/issues/65)の意味論の設計。
英語版（正）: [English](../../en/design/ci-evidence.md)。

責務分担、ソース本文の契約、証拠元・対象IDの変更での再承認、厳格な結果集約は
確認済み。[確定仕様](spec.md)の更新、配送形式、適合ベクトルは
[#66](https://github.com/ut-issl/inka/issues/66)で扱う。

## 責務分担

証拠元がテストを選択し、自身の環境で実行する。証拠元のアダプターが、人間が
確認できるテスト契約と対応する実行結果を出力する。GitHub Actionsが配送し、
inkaが取り込んだ版を論証・人間の承認と照合してオフラインで評価する。

証拠元と論証は別リポジトリでよい。取り込み済みの証拠を評価するために、inkaは
証拠元のcheckout、コンパイラ、テストランナー、ネットワークを必要としない。
証拠元を編集しただけでは評価は変わらず、更新された証拠の取り込みが必要になる。

結果は選択されたテストの実行結果を述べる。命題に対するテストの適切さを証明する
ものではなく、その判断は人間のbind承認が担う。

## 確認可能な契約

IFはファイル全体と個別テストの契約を扱う。抽出は証拠元の責務であり、inkaが
言語固有の式を解析・実行することはない。

契約は空でないUTF-8のソース文字列とする。ファイルなら全内容、
個別テストなら関連属性・テストパラメータを含む定義を渡す。各アダプターが
正確な抽出範囲を定義する。扱えない構文を対応済みとせず、行単位の正規表現で
関数の境界を推測しない。

例えばRustのproptestでは、選択したマクロ内テストのstrategyと本体を含める。
Pythonでは選択したテストのデコレータを含める。JavaScriptでは、選択したケースを
説明するために必要なテスト宣言をコールバックとともに含める。具体的な抽出方式は
各言語のIssueで決めるため、この例でパーサーや結果取得方式を確定するものではない。

外部ヘルパー本体は暗黙に含めない。捕捉した実行依存範囲の変更は
[#39](https://github.com/ut-issl/inka/issues/39)で扱う。fixture本体や動的に生成される
入力など、抽出から省かれる文脈を証拠元が明記する。

ハッシュ値だけでなく、内容を人間が確認できることが必要である。今回の実装は
消費側へ内容を提供し、承認CLIは[#27](https://github.com/ut-issl/inka/issues/27)で扱う。

## 内容のハッシュ

interfaceハッシュには証拠元ID、対象ID、人間が確認する内容を含める。ソース本文は
CRLFをLFへ置換するだけとし、単独CR、コメント、Unicodeの正規化状態、字下げ、
行末空白は内容として残す。正確なフレーミング、抽出規則のID、ドメインタグは#66で
定義し、各アダプターが個別に推測しない。

bindのview_hashは凍結済みv1のままとする。命題の説明・注釈、interfaceの生digest、
現在は空の仮定リストを含む。run ID、結果、環境情報、closureハッシュは承認契約に
混ぜない。証拠元と対象の識別はproviderのinterface digestへ含め、既存ベクトルを
書き換えない。

本文が同じでも、選択した証拠元や対象を変更すれば再承認が必要である。
ローカルで配送先を選ぶ別名だけの変更は、基底となる証拠元・対象の変更ではない。
同じ証拠元・対象・契約の新しい結果は既存の承認で評価できる。別リポジトリの証拠を
同じ出自に見せかけず、アダプターは実際の証拠元を保持する。

## 証拠の識別と版

| 概念 | 役割 |
| --- | --- |
| 証拠元 | 証拠を生成するリポジトリ・プロジェクト |
| 対象ID | 証拠元の中で選択する契約 |
| ソースの版 | テストした版。論証側の版とは異なる |
| 実行ID | workflowの実行・試行を区別する |
| interfaceハッシュ | 人間が確認する契約内容を識別する |
| ケース・環境ID | 対象に必要な実行を識別する |

ローカルの別名の重複や解決の競合は入力エラーとする。任意の証拠元を選んだり、
別の版へ黙って切り替えたり、失敗時に過去の成功した実行を探したりしない。

この未署名プロトコルでの出自は記録情報である。digestの再計算は内容の矛盾を
検出するが、実行者の認証や全実行の報告を証明しない。署名は
[#38](https://github.com/ut-issl/inka/issues/38)の領域である。

## 実行範囲と結果

証拠元が必要なケースと環境を明示し、それぞれの結果を報告する。
少なくとも1件の実行が必要であり、必要な全実行がpassした場合のみ対象をpassとする。

| 観測した状態 | bindへの意味 |
| --- | --- |
| 必要な全実行がpass | 証拠によって成立し得る |
| 必要な実行が1件でもfail | 証拠によって成立しない |
| 必要な実行がskipまたはcancel | 証拠によって成立しない |
| 必要な実行の結果が欠落 | 証拠によって成立しない |
| 同じ実行に矛盾・重複した結果 | 入力不正として評価を中断 |

必要な実行集合を成功結果だけから推測しない。最初のケースで実行が中断した場合、
完了したケースだけに必要集合を縮めてはならない。正しく集合を宣言する責務は
証拠元にある。inkaは実行しないプロジェクトのケースを独立に列挙できない。

再実行・workflowの試行は区別し、採用する試行を明示する。別の試行の成功を
寄せ集めない。matrixを1対象として扱う場合、必要集合を明示し、ソースの版と契約内容を
一致させる。特にfilterやskipが可能な場合、jobの終了コードから関数ごとのpassを
推定してはならない。

結果は実際に実行した内容へ結び付ける。実行中にファイルが変わった場合、終了後の
ハッシュだけで以前の結果を新内容へ付け替えてはならない。適切な実行境界で捕捉し、
実行前後の内容の不一致を拒否するか、同等の結び付けを保証する方式を明記する。

## 評価例

次の表はノードが期限切れでなく、現在のハッシュにdeclineがない場合を示す。
既存の承認定足数・拒否権・期限の規則は維持する。

| 取り込んだ証拠と承認 | 評価 |
| --- | --- |
| ファイル内容A、対応承認、必要な全ケースがpass | 成立 |
| 関数内容A、対応承認、必要な全ケースがpass | 成立 |
| 対応承認あり、必要な結果がfail | 未成立。証拠の失敗 |
| 対応承認あり、必要ケースが欠落またはskip | 未成立。証拠が不足・非pass |
| 証拠はpass、承認なし | 未成立。承認なし |
| 内容Bを取り込み、承認はAのものだけ | 未成立。承認がstale |
| 内容Aのまま、新実行がpass | 承認維持。成立 |
| 内容Aのまま、新実行がfail | 承認維持。未成立 |
| 証拠元だけ編集し、取り込み済み内容はA | 編集前と同じ評価 |
| 同じ内容で別の証拠元・対象へ変更 | 変更したinterfaceを承認するまで未成立 |
| 配送内容と申告digestが不一致 | 不正なbundle。評価を中断 |
| 参照先の証拠が存在しない | 未成立。証拠なし |

両方を計算できる正常な入力がある場合、承認と証拠の原因を独立に報告する。
承認のstaleをテスト失敗と呼ばず、同じ契約内容のテストが失敗しただけで再承認を
要求しない。

## 環境情報

lockfileハッシュを含む環境情報は任意であり、初期IFでは承認の有効性や証拠の成立条件を
変えない。言語・パッケージマネージャーを制限せずに記録できる。環境変更の警告・エラー
ポリシーは後続作業とする。lockfileハッシュで実行環境全体を捕捉したとは主張しない。

## 言語別アダプター

初期対象はRust/proptest、Python/pytest、JavaScript・TypeScript/Vitestとする。
各実装Issueで抽出範囲とrunner連携を定義する。未実行のテストへ成功結果を暗黙に
拡張してはならない。
