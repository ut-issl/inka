# inka — 未決事項

未決定の項目を、現在の暫定スタンスと、決着させる作業とともに列挙する。
英語版(正): [English](https://www.space.t.u-tokyo.ac.jp/inka/design/open-questions/)

## DSL と意味論

- **子の多重集合 vs 集合。** 同じ子を2回参照したい例はまだ無い。暫定: 集合とし、
  重複は error。実際に多重度が必要な論証が現れた時のみ再検討。
- **values の型と単位。** 値は任意の TOML 値を受け付け、TOML 表記のまま展開される
  (`"0.05 deg (3σ)"`、`42`、`[1.5, 2.0, 3.25]`)。数値パラメータやベクトルを
  引用符なしで書ける。単位に構造を与えるかは未決。ガード: values は共有リテラル
  定数のためのもの — 計算・検証される値は evidence provider の領分であり、values を
  影の provider に育てない。

## ポリシー

- **ポリシーファイルの形式と置き場。** `inka.toml` から参照する専用ファイルが有力。
  形式は未決。ポリシー言語の作業で決着。
- **タグの語彙。** 現在タグは自由語彙。チームが閉じた語彙を宣言できるようにするか
  (未知タグをセレクタ側 warning でなく error にする)は未決。

## 証拠

- **bind の description と言明の二重性。** description(人間側契約)が証拠の主張を
  再述しがち。設計上は両方が承認時に提示されるので冗長ではない。書き味の観察として
  記録し、注視する。
- **環境ノードの粒度。** 外部ライブラリは lockfile ハッシュを持つ単一の環境ノードと
  想定中。より細かい粒度が要るかは未決。
- **closure ハッシュの限界。** 実行時トレースの閉包は実行された経路のみを反映する。
  ネイティブ拡張は不透明(環境ハッシュでカバー)。証拠が読むデータファイルは明示的な
  組み込みが必要 — まずはデータファイル捕捉なしで始め、限界として記録する。
- **graphcal を input に。** 単位・次元検査付きの DAG 型リアクティブ計算言語
  [graphcal](https://graphcal.org/docs/)(`.gcl`)を inka の input として選べる
  ようにするかは検討中の選択肢。採否も統合の形([calc 証拠](calc-evidence.md)の第2の
  producer か、共有 values の供給源か、別の何かか)も何も決まっていない。inka の
  運用規律に graphcal 側の機能(安定したインターフェースハッシュや機械可読
  エクスポートなど)が必要になる場合、graphcal 側へ PR を出すことも選択肢に含める。

## 監査と運用

- **アンカリングの強度。** 軽量ハッシュチェーンはローカルでの削除を検出可能にする。
  透明性ログへの強化は予約された差し込み口であり、審査が要求したら採用する。
- **LLM lint の override UX。** 理由をログに残す人間の override は概念として存在する
  が、具体的なインターフェースは未決。
- **承認時の大きな仮定集合。** 集約された仮定集合が大きい場合の提示方法(グルーピング、
  diff のみ表示)— まず素朴に作り、使用感から決める。
