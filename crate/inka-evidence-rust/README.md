# inka-evidence-rust

Emits [inka test evidence](../../docs/en/design/test-evidence.md) v1 JSON
from a Rust test run driven by [cargo-nextest](https://nexte.st). The
adapter runs on the source repository's runner, typically inside
`capsula run`; storing and delivering the evidence file is capsula's
responsibility.

```console
$ inka-evidence-rust --output evidence.json \
    --provenance source_revision=$(git rev-parse HEAD) \
    -- --features extra
```

Everything after `--` is forwarded verbatim to both `cargo nextest list`
and `cargo nextest run`, so filters and feature flags apply to the
declaration and the execution alike. Test failures are evidence, not
errors: the exit status is zero whenever the evidence file was written.

## Requirements

- `cargo-nextest` on `PATH` (the suite kinds, listing JSON and JUnit
  output this adapter consumes are nextest's; plain `cargo test` offers no
  stable machine-readable output).
- A repository nextest configuration must not override `junit.path`; the
  adapter enables JUnit output itself and reads it back from the selected
  profile's store directory.

## What is declared and what is reported

The required execution set is declared from `cargo nextest list`, never
inferred from results:

- a test selected by the run's filters is declared, and its outcome comes
  from the run's JUnit report (`pass` / `fail`);
- an `#[ignore]`d test that the filters would otherwise select is declared
  with outcome `skip` (run it with `--run-ignored all` to collect a real
  result);
- a declared test the run never reported — the run aborted or was
  cancelled midway — keeps a missing outcome, which never establishes a
  bind;
- a test excluded by the filters is not declared at all.

Each run records one execution per test, labeled by `--case` (default
`default`). Runs of the same tests under different configurations — other
feature sets, platforms — are separate evidence files with distinct case
labels; merging them into one multi-case file is a later step of the
delivery flow.

## Test-id construction

```text
<nextest binary-id>::<test path>
```

For example `sample::tests::passes` (lib target) or
`sample::props::add_commutes` (integration-test target `props` of package
`sample`). The ids stay opaque to inka. If two suites collide once joined
— a module in one target shadowing another target's name — the adapter
fails explicitly; rename one side.

## Contract bodies

The body is the test's own definition, sliced verbatim from the source
file, attributes included. Two shapes are supported:

- a plain `fn` item marked by any test attribute (`#[test]`,
  `#[tokio::test]`, ...);
- a `fn` inside a `proptest!` block, parameter strategies included. A
  `#![proptest_config(..)]` line configures the whole block and is not
  part of any one test's body.

Module paths resolve as rustc resolves them: inline `mod` blocks,
`name.rs` / `name/mod.rs` files and `#[path]` overrides. Workspaces,
multiple test binaries and filters are supported; the mapping from a
suite to its cargo target comes from `cargo metadata`.

A test whose definition cannot be located — generated by a macro this
adapter does not understand (`rstest`, `test_case`, `macro_rules!`
wrappers, ...), or declared in a module shape it cannot resolve — is an
explicit error naming the test, never a guessed body. Doctests are not
run by nextest and are out of scope.

## Provenance

`--provenance key=value` records descriptive metadata (repeatable); the
`CAPSULA_RUN_ID` environment variable that `capsula run` exports fills
`capsula_run_id` unless an explicit entry already claimed it.
