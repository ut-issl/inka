# dogfood: ドッグフード論証を tests/fixtures/ から「生きたプロジェクト」の場所へ昇格させる

- **ラベル:** enhancement
- **マイルストーン:** M3(「ドッグフーディング開始」の最後のステップ)
- **依存:** #6(ドッグフード論証が存在すること)、および M3 の `inka eval` 関連の作業
  (論証が「生きる」ためには承認ログ+ポリシー+eval が存在する必要がある)

## 動機

ドッグフード論証は `tests/fixtures/` で生まれる(#6)。そこでは純粋に
パーサ/ハッシュ/eval テストの*入力データ*であり、M0〜M2 の間はこの場所が正しい。

M3 以降、その性質が変わる: ドッグフーディングとは、論証が `approvals/*.jsonl`、
`phase.inka`、`policy.inka` を従え、日常的に編集され、本物の `inka` コマンドで
承認されるようになることである。その時点でこれはもはやテストフィクスチャではなく、
**このリポジトリ自身の生きた inka プロジェクト**であり、人が編集し承認する生きた
プロジェクトが `tests/` の下にあるべきではない。

パスや CI が `tests/fixtures/` 前提で固まってから気づくのではなく、昇格を M3 の
計画されたステップにするために、今のうちに起票しておく。

## 昇格のタイミング(トリガー)

M3 のドッグフーディング開始時 — 具体的には、(手書きの jsonl テストフィクスチャでは
なく)論証に対する**最初の本物の承認レコード**を書く瞬間に昇格する。その瞬間より前は
「生きた」要素が何もなく、その瞬間より後は、遅らせるほどフィクスチャデータと
生きたデータの混同が育つ。

## タスク

- [ ] 移設先を決める: リポジトリルート(論証 + `approvals/` + `phase.inka` +
  `policy.inka` をトップレベルに置く、つまり実ユーザーのリポジトリと同じ見た目)か、
  専用の `dogfood/` ディレクトリか。デフォルト提案: **リポジトリルート**。
  ドッグフードリポジトリは inka プロジェクトのレイアウトの標準例を兼ねるべきだから。
- [ ] 論証ファイルを移動する。`tests/fixtures/` には本当にフィクスチャであるもの —
  意図的に壊したバリアント(診断テスト用)と小さな合成論証(eval シナリオテスト用)—
  だけを残す。
- [ ] 移設後にテストが生きた論証をどう消費するかを決める: その場で参照する
  (ドッグフードが統合テストを兼ねる — 生きた論証は常に `inka check` を通らなければ
  ならない)か、凍結したコピーをフィクスチャにスナップショットするか。
  デフォルト提案: `check` / `hash` のスモークテストは**その場参照**、安定した期待
  出力が必要なものはすべて合成フィクスチャで。
- [ ] CI のパスと、旧位置を指しているドキュメントを更新する。

## 受け入れ条件

- [ ] 生きた論証(+ approvals、phase、policy)が `tests/` の外にある。
- [ ] `tests/fixtures/` には壊したバリアントと合成論証だけが残っている。
- [ ] CI が生きた論証に対して `inka check`(eval が使えるようになったら eval も)を回している。
