# eval: 実行閉包ハッシュ — 界面不変のまま有効内容が変わったことの検出

- **ラベル:** enhancement
- **マイルストーン:** ドラフト07 の後(provider export 形式の拡張。`veriq:` / `ci:`
  両 provider に適用)
- **依存:** 07(provider 契約 / export スキーマ)、述語部分は M3 のポリシーエンジン

## 動機

bind 承認は証拠の*界面*(言明+正規化された本体)を固定する。これは意図的な設計である:
実装の真実性は再実行が担い、承認を実装内部に束縛すれば inka が殺したかった失効爆発が
戻ってくる。

しかし、ハッシュにも再実行にも捕まらない failure mode が1つある:
**テスト/検証が呼ぶヘルパが骨抜きにされ、界面は不変のまま、弱くなった証拠が pass し
続ける**ケース。Python の動的性(動的ディスパッチ、monkeypatch)のため静的な呼び出し
閉包の健全な計算は不可能だが、実行時トレースなら可能である。

## 仕組み

- provider の実行時(pytest プラグイン / veriq export)に、証拠ごとに**実際に実行された
  コードオブジェクトの集合**を記録(coverage 型トレース)し、正規化してハッシュした
  **`closure_hash`** を export に載せる。先行事例: pytest-testmon、Bazel の incremental
  test selection —「この証拠は何に依存しているか」を静的推測から実行された事実の記録に
  置き換える。
- **`closure_hash` は bind の束縛先に入れない。** 承認は界面への束縛のまま。無害な
  ヘルパのリファクタが承認を失効させてはならない。
- eval の診断: 界面ハッシュが不変のまま `closure_hash` が前回記録から変化していたら
  warning(「界面が変わらないままこの証拠の有効内容が変わった」)。骨抜き事件は
  少なくとも黙って通過しなくなる。
- ポリシー述語 **`closure-fresh`**: セレクタ単位で厳格化を選択できる。例
  `rule bind(#safety): closure-fresh` — safety タグ付きの bind だけ closure 変化で
  再承認を要求。固定の深さが、グローバル定数ではなくレビュー可能なポリシー宣言になる。

## 既知の限界(正直に文書化する)

- 1回の実行のカバレッジはその実行が通った経路を反映する: 非決定的・データ依存の分岐は
  実行間で異なりうる。行粒度でなく**コードオブジェクト粒度**でハッシュして安定させる。
- ネイティブ拡張は不透明 — 環境/lockfile ハッシュでカバーする。
- 証拠が読むデータファイルは明示的な組み込み(入力宣言またはファイルハッシュ捕捉)が
  必要 — まずは対象外とし、限界として記録する。

## 受け入れ条件

- [ ] 両 provider の export に `closure_hash` が存在する。
- [ ] 界面不変+closure 変化で eval の warning が発火する(骨抜きヘルパのフィクスチャで
      テスト)。
- [ ] `closure-fresh` 述語が実装され、スナップショットテストされている。
- [ ] 「closure を束縛先に入れない理由」が rustdoc に記録されている。
