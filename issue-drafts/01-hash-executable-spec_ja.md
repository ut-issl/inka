# hash: 局所ビューハッシュ(v1)を「実行可能な仕様」として実装する

- **ラベル:** enhancement
- **マイルストーン:** M0(仕様凍結 — コードファーストに再解釈)
- **依存:** 04(ドッグフード論証)— v1 を凍結する前に、実際の論証を書いて契約データモデルを検証しておくこと

## 動機

ロードマップ(M0)ではコードより先に `spec/hash.md` を書くことになっているが、代わりに
**リファレンス実装そのものを仕様とする**。凍結物はゴールデンテストベクタと
ドメイン分離タグの `v1` であり、散文の文書では**ない**。
ベクタが通り続ける限り、コードは自由にリファクタリングしてよい。

散文は曖昧になりうるがコードはそうではない。またプロパティテストは、文書では
記述しかできない不変条件(順序非依存性、冪等性)をテストとして固定できる。

## 契約データモデル(前提。Issue 04 で確定させる)

ハッシュは DSL の**構文**からは意図的に絶縁されている: ID とタグを含めず、子の順序を
無視するのはまさに、rename・並べ替え・将来の表層構文の変更が承認を失効させないため
である。ハッシュが依存する**のは**抽象的な契約モデル — 契約がどの情報から成るか
(concept §3.1)である:

| 種類 | ハッシュ入力 |
|---|---|
| `structure(N)` | desc(N) + 期限注釈 + 子の desc 群の多重集合 |
| `bind(N)` | desc(N) + source の言明 + 総仮定集合 |
| `fiat(N)` | desc(N) + 期限注釈 |

この Issue に着手する前に、Issue 04 で以下に答えが出ていること:

1. 成分の十分性(承認の界面に載るべきものが他にないか)
2. 期限注釈をハッシュ入力バイト列にする際の正規形
3. 子の多重集合 vs 集合の意味論(同じ子の二重参照を許すか)

**既知の制約(受け入れる):** `bind` については framing(ソート済み・長さ接頭辞付きの
3成分)を今凍結するが、「source の言明」「総仮定集合」の中身は veriq 連携(M8)で
初めて確定する。それまで bind のベクタは合成文字列を使う。

## この Issue で確定させる設計判断

各判断は**モジュールの rustdoc に、1行の理由とともに**記録すること
(別の設計文書は作らない):

1. **入力単位**: 局所ビュー = 自ノードの正規化 description + 期限注釈 +
   子の正規化 description の*多重集合*。
2. **文字列正規化 — 1レジーム(description は常にフェンス付きブロック。裸の
   1行形式は DSL に存在しない)**: UTF-8、NFC、CRLF→LF、行末空白の除去、共通
   インデントの剥ぎ取り、先頭末尾の空行の除去のみ。**内部の改行と空白は verbatim に
   保存する**(「見たままが承認対象」)。markdown-AST での正規化はしない — 凍結仕様に
   CommonMark 依存を持ち込まないためで、代償として description の再改行(reflow)は
   ハッシュを変える。(コメントは字句解析段階で落ちるため対象外。)
3. **子の順序**: 正規化 description のバイト列をキーに子をソートし、ハッシュを
   順序非依存にする(`supported-by` の並べ替えは何も失効させない)。
4. **framing**: 区切りの曖昧さを排除するための長さ接頭辞付き連結(`len || bytes`)。
   先頭にドメイン分離タグ(`"inka:structure:v1"`、`"inka:bind:v1"`、
   `"inka:fiat:v1"`)を付けて SHA-256 にかける。
5. **非包含/包含**: ID とタグ(`#safety`)はハッシュに含めない。期限注釈
   (`until:` / `promote:`)は Issue 04 で決めた正規形で含める。
6. **バージョニング**: `v1` はドメイン分離タグに焼き込む。正規化規則を将来変更する
   場合は必ず `v2` として並存させ、in-place の変更はしない。
   (逃げ道: 本物の承認レコードが溜まり始める M3 のドッグフーディング開始までは、
   v1 の改訂はベクタの再生成だけで済み、誰の承認も失効させない。)

## 実装メモ

- `LocalView` 構造体(素の文字列)上の純関数。**パーサ非依存** — 入力は抽出済みの
  description / 注釈なので、このモジュールは DSL パーサが存在する前に作れる
  (ロードマップの M2 より順序を繰り上げる)。
- `LocalView` の description は素の文字列。DSL の description 形式は1つ(フェンス付き
  ブロック)なので、形式タグは不要。
- 値埋め込み(values TOML から解決される `{$var}`)は抽出段階、つまり正規化・ハッシュの
  **前**に行う — `LocalView` は展開済みの description を受け取り、ハッシュはプレース
  ホルダを見ない。帰結として、値の変更はその値を参照する契約の承認(+その直接親の
  structure 承認)を正確に失効させる。
- クレート: `sha2`、`unicode-normalization`。
- 3種の view_hash(`structure` / `bind` / `fiat`)をすべて計算する。

## プロパティテスト(proptest)

- インデントの深さ・行末空白・CRLF/LF の違いではハッシュ不変。ただし内部の改行・
  空白の変更では**変化する**。
- 子の並べ替えでハッシュ不変。
- description の1文字の変更でハッシュが変化。
- 正規化の冪等性: `normalize(normalize(x)) == normalize(x)`。
