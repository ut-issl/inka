# dogfood: inka 自身の設計論証を inka DSL で書く

- **ラベル:** documentation
- **マイルストーン:** M0
- **依存:** なし — **これが v0 の起点**
- **ブロック対象:** 01(hash v1)— ここでの発見が、ハッシュが凍結する契約データモデルを確定させる

## 動機

inka 自身の設計論証(inka-concept.md の内容)を inka の DSL で書き、テスト
フィクスチャ兼カノニカルな例として使う。パーサは不要。自分が最初のユーザーに
なることが、DSL の書き味の問題を最速で露見させる — そして構文の手直しは、
lexer / パーサが存在する前のこの段階が最も安い。

この Issue にはもう一つ、より重要な仕事がある: **hash v1(Issue 01)が凍結する
契約データモデルの検証である。** ハッシュは DSL の*構文*からは意図的に絶縁されている
(ID 非包含、子の順序無視)が、*契約がどの情報から成るか* — description、期限注釈、
子の description 群 — には依存する。実際の論証を手で書くことは、何かを凍結する前に
以下を確認する最も安い手段である:

- 契約の成分が十分か(承認の界面に載りたがるものが他にないか)
- 期限注釈の語彙(`until:` / `promote:`)の表現力が足りていて、自明な正規形を
  持つか
- ノードが同じ子を二度参照する必要がありうるか(ハッシュ入力の多重集合 vs 集合の
  意味論)

## タスク

- [ ] フラットブロック構文で論証を書く: 1ブロック = 1命題の契約 + 子への参照
  (`supported-by`)、葉のインライン記述(`evidence:` / `assumption:`)、タグ
  (`#...`)、期限注釈(`until:` / `promote:`)。
- [ ] `tests/fixtures/` に配置する。
- [ ] 書いていて見つかった構文上の問題点を記録する(PR のノートまたはフォロー
  アップ Issue)— これらは lexer / パーサの設計に直接フィードバックされる。
- [ ] 上記の契約モデルに関する3つの問い(成分の十分性、注釈の正規形、多重集合の
  意味論)への答えを PR の説明に明示する — Issue 01 はこの答えから始まる。

## 受け入れ条件

- [ ] 完全なドッグフード論証が `tests/fixtures/` に存在する。
- [ ] 構文上の問題点(あれば)が Issue として起票されている。
- [ ] 契約モデルの3つの問いに答えが出ており、Issue 01 のブロックが外れている。
