# hash: ゴールデンテストベクタ — 独立検証してから凍結する

- **ラベル:** enhancement
- **マイルストーン:** M0(仕様凍結 — コードファーストに再解釈)
- **依存:** 01(局所ビューハッシュ v1)

## 動機

コードを仕様とする方式では、ゴールデンベクタこそが凍結された仕様*そのもの*になる:
実装はいつでも書き直してよいが、ベクタは決して変えてはならない
(変更は `v2` を意味する)。実装からベクタを生成することの唯一のリスクは、
実装の癖(例: NFC のつもりが NFD、serde のマップ順序)が黙って仕様に化けることで、
少数サンプルの独立検証が最小コストでこの穴を塞ぐ。

**`bind` ベクタについての注記:** bind ハッシュの framing(ソート済み・長さ接頭辞
付きの3成分)は v1 で凍結するが、「source の言明」「総仮定集合」の実際の中身が
確定するのは veriq 連携(M8)である。したがってここでの bind ベクタは合成文字列を
使う — 凍結するのは framing であって、veriq 側の中身ではない。

## タスク

- [ ] リファレンス実装から10個以上のベクタを生成する。カバレッジ:
  - 3種すべて: `structure` / `bind` / `fiat`
  - 期限注釈(`until:` / `promote:`)あり/なし
  - 子の順序だけが異なり、同一ハッシュに**ならなければならない**ペア
  - 1文字だけ異なり、異なるハッシュにならなければならないペア
  - NFC を検査するための非 ASCII の description(日本語テキスト、結合文字)
- [ ] **Rust 実装を使わずに 2〜3 個のベクタを独立に再導出**し(手計算または
  使い捨ての Python スクリプト)、一致を確認する。
  使い捨てスクリプトは PR の説明かコメントに残し、リポジトリには入れない。
- [ ] ベクタを `tests/golden/` にコミットし、テストスイートに組み込む。
- [ ] 以後 `tests/golden/` は追記専用として扱う。(既存ベクタを変更する PR を
  落とす CI ガードは別のフォローアップ Issue とする。)

## 受け入れ条件

- [ ] ベクタがコミットされ、CI で通っている。
- [ ] 2〜3 個のベクタの独立検証が PR に記録されている。
